# Decisions: 1 vs 1 PvP

- Date: 2026-10-29
- Status: Design recorded; implementation deferred until PvP Azure resources are approved/available.

## Purpose

Add a player-versus-player mode to the Mango Stone main menu. Players create or join a private match using a six-digit numeric room code. This document records decisions made during the requirements interview so a later PvP request can resume without repeating them.

## Confirmed decisions

### Menu and matchmaking

- Add a `1 vs 1` main-menu entry with a small white sparkling `NEW` marker to its left.
- Opening it presents two choices: create a match or join one.
- Creating a match generates a random six-digit code. The creator immediately joins as player 1 and waits in the room.
- Joining asks for the six-digit code; the second player joins as player 2. The same flow must work on desktop and mobile.
- A room with no opponent expires after 10 minutes and informs its creator.

### Class selection

- When both players are in the room, they choose a class concurrently for up to 10 seconds.
- Use the existing Warrior, Assassin, and Demonist class-selection illustrations and descriptions.
- A player can confirm early; when both confirm, proceed immediately. At timeout, lock the currently selected class, defaulting to Warrior if none was selected.
- During combat, show each player's Entra display name and profile photo in the hero panel. Each client may retrieve its own photo through Microsoft Graph and share it temporarily with the opponent over the realtime channel. If the photo is unavailable or consent is not granted, show that player's class portrait instead.
- Profile photo retrieval requires an appropriate delegated Microsoft Graph permission; `User.Read` is documented for retrieving a signed-in work/school user's photo. Organizational consent may be required. See [Microsoft Graph profile photo permissions](https://learn.microsoft.com/en-us/graph/api/profilephoto-get?view=graph-rest-1.0).

### Deck draft

- Keep the existing class-based 30-card starter deck.
- Each player drafts privately and independently, with no draft timer. Each offer contains two different random cards from the shared pool and that player's selected-class pool only; never offer another class's exclusive cards.
- The pool excludes token cards and includes boss-tier cards.
- Selecting one offered card adds it to the deck. Passing discards the offer and presents a new random pair without adding a card. Repeat until the deck has exactly 35 cards.
- A card may appear at most twice in a player's complete deck, including the starter deck. Once a player owns two copies, exclude that card from future offers.
- Start combat only after both players have completed their 35-card decks.

### First-player selection and opening hand

- After both decks are complete, show three selectable face-down cards marked 1, 2, and 3.
- Both players choose concurrently under a five-second timer. The higher number determines first player.
- A number becomes unavailable as soon as the server accepts one player's choice; the other player must choose one of the remaining numbers. If both submit the same number nearly simultaneously, accept the first server-side choice and let the other player choose again while the same five-second timer continues.
- If a player has not chosen at timeout, randomly assign an unused number. If both have not chosen, assign two distinct unused numbers.
- Give the second player one extra opening card. Both players may redraw their entire opening hand once.

### Combat and match lifecycle

- Reuse the existing PvE combat rules symmetrically for both players: health, mana progression, six-minion field limit, class abilities, card effects, and combat rules.
- Give each turn 20 seconds. The server ends a turn on timeout; hiding the tab does not pause the clock.
- Resolve actions and validate mana, turn ownership, card legality, and the resulting combat state on the server, then broadcast the committed state to both players.
- A disconnected player immediately forfeits; the opponent wins. Add an in-game surrender action with a confirmation step; confirmed surrender awards the opponent a win.
- If one hero reaches zero health, the other player wins. If both heroes reach zero in the same effect, the result is a draw.
- Show a result screen with `Rematch` and `Main Menu`. Start a rematch from class selection only after both players accept.

## Deferred implementation and prerequisites

- No PvP code or Azure resources are to be added as part of this interview. The user chose to defer implementation rather than add cloud resources now.
- The intended online architecture is realtime synchronization with Azure SignalR, a server-authoritative PvP API, and temporary match/session state in the existing Cosmos DB account. Match state storage is separate from expedition progress and leaderboard records.
- The current Static Web Apps managed API supports HTTP triggers only. A separate Azure Functions app is needed for the intended SignalR/serverless setup and server-driven turn timeouts. This may add Azure resource and usage costs. See [Static Web Apps API constraints](https://learn.microsoft.com/en-us/azure/static-web-apps/apis-functions) and [Azure SignalR JavaScript Functions quickstart](https://learn.microsoft.com/en-us/azure/azure-signalr/signalr-quickstart-azure-functions-javascript).
- When PvP work resumes, confirm that the separate Functions app and SignalR resource can be provisioned, confirm the Cosmos database/container to use for temporary match state, and configure required Entra/Graph consent. Preserve the game-design decisions above unless the user changes them.

## Follow-up details to settle when implementation resumes

- Define reconnect behavior only if the immediate-forfeit rule changes; current decision is immediate forfeit.
- Set cleanup/retention for completed match documents and rematch invitations. Waiting rooms expire after 10 minutes.
- Verify the complete draft candidate list against current card definitions, especially class fusion cards, before implementing the random pool.
- Specify the exact Entra app registration redirect origins and Graph delegated permission consent path for local and deployed PvP clients.
